FighterFish · module/osgi-javaee-base

osgi-javaee-base, el núcleo de despliegue híbrido

El módulo base sobre el que se construyen los contenedores web, EJB y los extenders de JPA, JTA, JDBC y recursos. No despliega nada por sí mismo: define el ciclo de vida de los extenders, el contenedor que decide qué deployer atiende cada bundle, la plantilla de despliegue sobre la API de GlassFish y la forma de leer un bundle como si fuera un archivo Jakarta EE.

Rol del módulo

FighterFish sigue el patrón extender de OSGi: un bundle observa a los demás y, cuando reconoce uno que contiene artefactos Jakarta EE, lo despliega en el contenedor correspondiente de GlassFish. Este módulo aporta las cuatro piezas comunes a todos esos extenders:

  1. Ciclo de vida de extenders. ExtenderManager espera a que GlassFish esté STARTED y entonces arranca todos los servicios Extender registrados (los de este módulo y los de los demás). Los detiene cuando GlassFish anuncia PREPARE_SHUTDOWN.
  2. Contenedor de aplicaciones híbridas. JavaEEExtender sigue los bundles activos y OSGiContainer elige, por ranking de servicio, el OSGiDeployer que sabe manejar cada bundle.
  3. Plantilla de despliegue. AbstractOSGiDeployer, OSGiDeploymentRequest, OSGiUndeploymentRequest y OSGiDeploymentContext convierten un bundle en una llamada a Deployment.deploy() de GlassFish. Las subclases solo aportan el contexto y los class loaders específicos.
  4. Lectura del bundle como archivo. OSGiBundleArchive y OSGiJavaEEArchive implementan ReadableArchive sobre la API de bundles, respetando Bundle-ClassPath y fragmentos.

Flujo de arranque

Cuando Felix arranca el bundle, el activador registra el manejador de URLs embeddedjar:, crea el ExtenderManager y registra el JavaEEExtender como servicio. Ningún extender empieza a trabajar hasta que GlassFish está completamente arrancado: así se evita desplegar aplicaciones con el servidor a medio iniciar.

El orden de los dos últimos pasos es deliberado: los extenders arrancan antes de registrar el listener de eventos. El comentario del código explica que, al revés, podía producirse un interbloqueo si GlassFish enviaba PREPARE_SHUTDOWN mientras startExtenders() estaba en curso.

Limpieza en caso de error. Si Deployment.deploy() devuelve null y el bundle no venía como directorio, OSGiDeploymentRequest.deploy() borra el directorio expandido en su bloque finally. Como GlassFish "se come" muchas excepciones, el fallo se detecta por el null y el mensaje del ActionReport, no por una excepción.

Flujo de repliegue

Cuando el bundle sale de ACTIVE/STARTING (se detiene o desinstala), el tracker llama a removedBundle. El repliegue es síncrono, para no competir con el apagado del bundle.

sequenceDiagram
  autonumber
  participant BT as BundleTracker
  participant H as HybridBundleTrackerCustomizer
  participant X as JavaEEExtender

  participant AI as ApplicationInfo (GlassFish)

  H->>H: future.get(timeout) — por defecto 10 000 ms
  alt timeout
    H->>H: cancel(true); si no se pudo cancelar, get() sin límite
  end
  H->>X: undeploy(bundle) si hubo resultado o c.isDeployed(bundle)
  X->>C: undeploy(bundle)
  C->>C: applications.remove; desregistra el servicio OSGiApplicationInfo
  C->>D: undeploy(info) usando el deployer guardado en info
  D->>D: raiseEvent(UNDEPLOYING)
  D->>U: createOSGiUndeploymentRequest(...).execute()
  U->>U: preUndeploy()
  U->>U: getDeploymentContextImpl() — crea un contexto nuevo
  U->>AI: stop(dc); unload(dc)
  U->>GD: undeploy(appName, dc)

El tiempo de espera se configura con la propiedad del framework org.glassfish.osgijavaeebase.deployment.timeout (milisegundos). Además del Future, se comprueba isDeployed(): un DeployerAddedThread puede haber desplegado el bundle sin pasar por el tracker (caso GLASSFISH-18159).

Deployers dinámicos y estados

OSGiContainer no conoce los deployers de antemano: los descubre como servicios OSGiDeployer. Cada contenedor concreto (por ejemplo OSGiWebDeployer) se registra con un service.ranking, y el contenedor mantiene la lista ordenada de mayor a menor ranking. Cuando aparece o desaparece un deployer, se lanzan hilos que vuelven a desplegar los bundles afectados.

AbstractOSGiDeployer.unregister() llama primero a undeployAll() y después desregistra el servicio. Si lo hiciera al revés, el contenedor ya no podría obtener el deployer para replegar sus aplicaciones.

Estados que publica cada deployer

La enumeración AbstractOSGiDeployer.State marca las transiciones que se notifican mediante raiseEvent(). En este módulo el método está vacío; OSGiWebDeployer lo sobrescribe para publicar los eventos de Event Admin que exige la especificación de WAB (WABEventPublisher).

Class loaders

GlassFish usa dos class loaders durante un despliegue: uno temporal, para escanear anotaciones en la fase PREPARE, y uno final para ejecutar la aplicación. OSGiDeploymentContext anula la creación estándar (createDeploymentClassLoader y createApplicationClassLoader no hacen nada) y devuelve los que la subclase fija en setupClassLoader().

BundleClassLoader sobrescribe loadClass, getResource y getResources (no los find*). Así incluso las clases del JDK o del sistema pasan por el wiring del bundle, y se respeta el control de exportaciones de OSGi. Nunca define clases: getClassLoader() de una clase nunca devolverá esta instancia.

Modelo de archivos

GlassFish trabaja con ReadableArchive. Este módulo ofrece dos vistas de un bundle:

  • OSGiBundleArchive: el contenido físico del bundle, entrada por entrada, mediante Bundle.getEntry y getEntryPaths. No mezcla fragmentos.
  • OSGiJavaEEArchive: una vista "aplanada" para Jakarta EE. Recorre el Bundle-ClassPath efectivo del host y de sus fragmentos y deja que la subclase (WAB, EJBBundle) construya el mapa de entradas que verá GlassFish.

Nombre del archivo. OSGiBundleArchive.getName() devuelve Bundle-SymbolicName_Bundle-Version (o la ubicación si no hay nombre simbólico). Ese nombre se convierte en el nombre de la aplicación en GlassFish (DeployCommandParameters.name).

ExtenderManager

Arranca todos los servicios Extender cuando GlassFish está listo y los detiene en el apagado. Es único para todo FighterFish: los extenders de los demás módulos solo se registran como servicio y este manager los pone en marcha.

JavaEEExtender

final class · Extender313 líneas

El extender de aplicaciones híbridas: detecta bundles activos y los envía al OSGiContainer.

  • start(): crea un executor de un solo hilo y un OSGiContainer (que publica como servicio), y abre un BundleTracker sobre los estados ACTIVE | STARTING.

2 · Contenedor

OSGiContainer

class486 líneas

Registro central de aplicaciones híbridas desplegadas y despachador hacia los deployers. Se publica como servicio OSGi para que otros módulos puedan consultarlo.

  • Estado: applications (bundle → info), regs (info → registro de servicio) y sortedDeployerRefs (deployers por ranking descendente).
  • deploy(bundle): descarta los bundles en STOPPING o ya desplegados. Elige el primer deployer cuyo handles() responde true y delega en él. Después guarda el deployer usado dentro del info y publica el OSGiApplicationInfo como servicio.
  • undeploy(bundle): quita la aplicación del mapa, desregistra su servicio y llama al mismo deployer que la desplegó.
  • OSGiDeployerTracker, DeployerAddedThread y DeployerRemovedThread (anidadas) mantienen las aplicaciones sincronizadas cuando aparecen o desaparecen deployers (ver deployers dinámicos).
  • isReady(bundle) considera listo un bundle ACTIVE, o STARTING si su Bundle-ActivationPolicy es lazy.
  • Todo el acceso es synchronized sobre la instancia: el comentario explica que no se sabe si el framework de despliegue de GlassFish admite peticiones concurrentes.
Colabora con
OSGiDeployer, OSGiApplicationInfo

OSGiDeploymentRequest

abstract class441 líneas

Petición con estado que despliega un bundle en GlassFish y deshace lo hecho si algo falla. execute() sigue este orden: preDeploy → prepare → deploy → postDeploy, y postDeploy se llama siempre.

  • prepare(): crea el archivo con makeArchive(), prepara los parámetros con getDeployParams(), expande si hace falta y crea el contexto con getDeploymentContextImpl(). Los parámetros se calculan antes de expandir para que el nombre de la aplicación sea el del bundle y no colisione con asadmin deploy --type=osgi (issue 10536).
  • expandIfNeeded(): si el archivo es un directorio, lo usa tal cual. Si no, lo expande con OSGiArchiveHandler.expand() en <datafile>/applications/bundle{id}-{lastModified}. Incluir la fecha de modificación evita reutilizar contenido obsoleto tras actualizar el bundle.
  • deploy(): llama a Deployment.deploy(dc) y construye el OSGiApplicationInfo con dc.getFinalClassLoader().
  • makeFile(archive) (estático): convierte la URI del archivo en File, o null si no es posible.

4 · Archivos

OSGiBundleArchive

final class · AbstractReadableArchive · URIable · Iterable1.035 líneas

Implementa ReadableArchive de GlassFish leyendo directamente del bundle (getEntry, getEntryPaths). Es la clase más grande del módulo.

  • Inicialización: calcula la URI solo si la ubicación es reference:file: y el fichero existe. El nombre es SymbolicName_Version.
  • Entradas: entries() recorre recursivamente con getEntryPaths, devuelve solo ficheros y evita un META-INF/ duplicado (FELIX-2935). Requiere que el jar tenga entradas de directorio (FELIX-1210); hay una implementación alternativa con findEntries desactivada.
  • Subarchivos: getSubArchive(name) devuelve un EmbeddedDirectoryArchive o un EmbeddedJarArchive, cacheados por nombre. Solo se admite un nivel de anidamiento.
  • EmbeddedJarArchive: lee el jar anidado con ZipInputStream y expone sus entradas con URIs embeddedjar:<uri-del-jar>!/<entrada>.
  • EmbeddedJarURLStreamHandlerService: abre esas URIs recorriendo el jar hasta la entrada pedida. El activador lo registra como servicio de manejo de URLs.
  • Iteración: iterator() genera un BundleResource por cada entrada de cada elemento del Bundle-ClassPath. Es la base del escaneo de recursos de los demás módulos.
  • getInputStream(): si hay fichero real, lo abre. Si no, genera un jar al vuelo con un pipe y un hilo (GLASSFISH-19662).

URIable, BundleResource, JarHelper, Constants
Usada por

Vista de solo lectura que combina un bundle host y sus fragmentos en un único archivo Jakarta EE. La subclase rellena el mapa entries en init(); esta clase implementa todo lo demás de ReadableArchive sobre ese mapa.

Observaciones del código

Hallazgos de la lectura, útiles para planificar mejoras. Ninguno impide el funcionamiento actual: los tests de integración pasan en GlassFish 8.0.4.

medioReferencias de servicio que no se liberan

OSGiContainer llama a context.getService() en deploy, undeploy, selectDeployer y los hilos de deployers, sin ungetService(). ExtenderTracker.removedService vuelve a pedir el servicio en vez de usar el objeto recibido. El contador de uso de los servicios solo crece; no rompe nada en la práctica, pero impide que un deployer se libere limpiamente.

medioHilos creados a mano

DeployerAddedThread, DeployerRemovedThread, el sondeo de GlassFishServerTracker (cuyo executor nunca se cierra) y los pipes de JarHelper.makeJar y OSGiBundleArchive.getInputStream crean hilos sin nombre ni gestión. Las excepciones de esos hilos se pierden.

bajoContexto nulo al expandir

En OSGiDeploymentRequest.prepare(), expandIfNeeded() se ejecuta antes de crear dc, así que OSGiArchiveHandler.expand(archive, target, dc) recibe null como contexto. Funciona porque la implementación heredada no lo usa, pero es frágil ante cambios en GlassFish.

bajoSondeo de arranque

ExtenderManager sondea GlassFish.getStatus() cada segundo. El comentario dice que es necesario para GlassFish < 4.0; en GlassFish 8 podría reemplazarse por el evento SERVER_READY.

bajoCódigo muerto

TempBundleClassLoader, ReflectiveClassFinder y OSGiBundleArchive.getEntryPaths2() no tienen usos en el repositorio. Además hay dos criterios distintos de "bundle listo": JavaEEExtender mira el evento LAZY_ACTIVATION y OSGiContainer.isReady mira la cabecera Bundle-ActivationPolicy. ReflectiveClassFinder además no funcionaría con el sistema de módulos de JDK 21 sin --add-opens.

bajoTipos crudos y APIs antiguas

Uso extendido de ServiceTracker, ServiceReference y Dictionary sin genéricos (con @SuppressWarnings("unchecked")), Properties como Dictionary y Globals para obtener servicios de GlassFish. Con OSGi R8 se puede tipar todo.

infoSerialización global

Todo despliegue y repliegue pasa por métodos synchronized de OSGiContainer y por un executor de un solo hilo en JavaEEExtender. Es una decisión consciente (no se sabe si Deployment es seguro en concurrencia) y explica que muchos bundles se desplieguen uno tras otro.

infoDetalles menores

El LOGGER de OSGiDeploymentRequest se crea con la clase OSGiUndeploymentRequest (mismo paquete, sin efecto). AbstractOSGiDeployer.undeployAll registra los fallos con el nombre de clase "WebExtender". OSGiApplicationInfo se registra con propiedades vacías, sin nombre de aplicación ni context path que permitan filtrar.
